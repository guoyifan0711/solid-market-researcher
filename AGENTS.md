# Solid Market Researcher

Use these conventions for market research and the market section of a marketing proposal. The user's current decision, scope and delivery requirements take priority. Keep project-specific facts and decisions in the project's own records.

## Start with the decision

Recover the brief, prior decisions, products, audience, geography, research period, data cutoff and delivery requirements. Ask short questions in dependency order when missing business intent would change the research route. Research public facts directly. Continue independent work while a necessary decision is pending.

Create a task card for each page or research question: the question, scope, required evidence, intended type of judgment, downstream uses, and evidence that could overturn the working hypothesis. A task card defines a question, not an answer to prove.

## Build the argument across the report

Connect market scale and change to mechanisms, regional and segment differences, priority audiences, competition and marketing choices. Each page answers one main question. Market pages can conclude on scale or direction; client actions belong where the evidence supports them.

Write a conclusion-led title, a short main conclusion, the useful visual, and supporting judgments with evidence. Keep APA original sources separate from the calculation trail. Necessary qualifiers stay beside the claim. Research instructions and revision history stay in workpapers.

## Preserve evidence and scope

Record the original publication, acquired version, exact location, date, data period, geography, category, population, unit, denominator, method, access state and Actual/Estimate/Forecast/Scenario status. A public abstract supports only what it discloses. Keep conflicting evidence and distinguish independent sources from repeated citations of one source.

Track Source, Evidence, Scope, Use, Claim, Location and Reference in the [evidence graph](skills/review-market-analysis/references/evidence-graph.md). Start the [substantive review](skills/review-market-analysis/references/source-grounded-review.md) from acquired original context, reconstruct its scope independently, and compare it with the current report sentence. Status flags and hashes bind records to versions; the analyst must still assess meaning and inference.

Direct quotations need original anchors. Derived numbers need reproducible inputs and formulas, with independent checks of units, denominator, year count and assumptions. A demand pool is distinct from annual purchases; revenue, shipments, sales and installed base retain their definitions. An analytical score retains its inference status.

Log inaccessible sources and their affected claims. Present acquisition gaps together by Part or research phase, with the most consequential sources first. Continue unaffected research and narrow dependent claims. Purchasing, contacting a supplier or using another party's access requires the corresponding authorization.

## Review changes and delivery

Use the [dependency table](skills/review-market-analysis/references/argument-dependencies.md) to check downstream text, calculations, visuals and summaries when an upstream finding changes. Run the executable checks for the affected scope and record what was actually checked. Inspect charts in their final display container.

Keep one current manifest for versions, hashes, approvals, open issues and publication readbacks. Use [project-state templates](skills/review-market-analysis/references/project-state.md) for new projects; preserve equivalent systems in existing projects. Approval attaches to a specific version. Analyst review, user confirmation and authorization to publish are separate states.

Before an authorized external write, compare the approved content with the candidate. Afterwards read back the actual target using the same explicit identity and check content and rendering. Local scripts neither grant authority nor publish content.

## Keep research out of the toolkit repository

Work in a separate private research directory. This repository contains generic skills, templates, tools and synthetic tests. Do not commit briefs, client names, acquired reports, source archives, research datasets, screenshots, credentials, private URLs, delivery snapshots or personal machine paths. Inspect the staged file list and commit metadata before every push. Ignore rules are a convenience; the staged review decides what is uploaded.

Preserve the user's chosen model. Delegate only when the user or applicable project instructions authorize delegation. When authorized, give bounded tasks and independently review returned evidence before adopting it.
